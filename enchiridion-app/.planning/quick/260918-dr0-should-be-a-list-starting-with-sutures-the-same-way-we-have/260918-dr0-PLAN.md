## Already-landed infrastructure — consume it, never re-invent it

Siblings 260918-dqx and 260918-dqy collided once by each declaring a same-named constant in two
different files. Do not repeat that. Everything below already exists on `main`:

- `availableFirst<T>(items, isAvailable)` in `enchiridion/lib/utils/content_availability.dart`.
  `ResourceTopicListScreen.build()` already calls it on its own `topics` input, so this plan needs
  **zero** ordering code — the suture entry leads automatically because it is the only entry whose
  `dataAssetPath` is non-null.
- `kComingSoonLabel` lives in `content_availability.dart` and is re-exported by
  `widgets/common/coming_soon.dart`. Do not declare another one anywhere.
- `ComingSoonStyle` (`title`/`body`/`icon`/`container` colour helpers), `ComingSoonBadge({compact})`,
  and `ComingSoonDim({dimmed, child})` in `enchiridion/lib/widgets/common/coming_soon.dart`. Use
  these instead of hardcoding alphas, scrims, or status text.
- `ResourceTopic.hasContent` (`dataAssetPath != null`) and `ResourceTopic.isComingSoon`
  (`!hasContent`). Branch on `isComingSoon`; never re-derive from `dataAssetPath` in UI code.
- `enchiridion/test/guards/available_before_coming_soon_guard_test.dart` already lists
  `availableFirst(kSurgicalInstrumentationTopics)` in its `_catalogs()` table, so the expanded
  catalog is covered by the repo-wide ordering invariant with no edit to that file.
