<objective>
Make the tab strip inside an opened topic list that topic's own SUB-TOPICS, and make the
content area swipe sideways between them.

Purpose: today `_OsceDetailScreen` puts every OSCE *station* in one `TabBar`, so opening
"Respiratory System" drops the user into a 12-tab strip of unrelated stations. The user's
follow-up message (sibling `260918-dr5`) says this directly: "the tab scroll feature is not for
the topics, it is for the sub-topics within each topic." Every other topic surface
(`ResourceTopicDetailScreen`, used by Sutures and IV Cannula) has no tabs at all — it renders
one 36- or 28-subsection wall of content in a single scroll.

Output: a shared `SubtopicTabsView` + pure `subtopicTabsFor()` derivation in
`lib/widgets/common/subtopic_tabs.dart`, consumed by the OSCE detail screen and by
`ResourceTopicDetailScreen`, so every topic in the app opens into swipeable sub-topic tabs.
</objective>

  <action>
Create `lib/widgets/common/subtopic_tabs.dart`, the shared "a topic opens into its own
sub-topics" surface. Give the library a dartdoc header stating that it is the single place the
app decides what a topic's sub-topics are, so new topic surfaces consume it rather than
inventing their own tab strip.

Expose three things:

1. `class SubtopicTab` — an immutable value type with `final String title` (the tab label) and
   `final Chapter? content` (the slice this tab renders, null when the topic has nothing
   written yet). Add a `const` constructor. It holds no `BuildContext` and imports no
   `material.dart` symbol beyond what `Chapter` already needs, so it is unit-testable.

2. `List<SubtopicTab> subtopicTabsFor({required ResourceTopic topic, Chapter? chapter})` — the
   pure derivation, applied in this precedence order and documented inline with the measured
   content shapes from `<context>`:
   - `chapter` non-null with 2 or more sections: one tab per section, label = section title,
     slice = a `Chapter` copied from the original (same id, title, icon, description, order,
     tags, chapterColor) carrying only that one section, unmodified.
   - `chapter` non-null with exactly 1 section that holds 2 or more subsections: one tab per
     subsection, label = subsection title, slice = a `Chapter` copied from the original
     carrying one `ChapterSection` that reuses the original section's id, title, order and
     color and holds only that single, unmodified `ChapterSubsection`. This is the branch the
     three real topic JSONs take — copying ids verbatim is what keeps `blockAnchorId` note
     anchors resolving after the split.
   - `chapter` non-null otherwise (no sections, or one section with at most one subsection):
     exactly one tab carrying the chapter unchanged, labelled with the chapter title when it is
     non-blank and the topic title otherwise.
   - `chapter` null with a non-empty `topic.outline`: one tab per outline entry, label = the
     entry, slice null.
   - `chapter` null with no usable outline: exactly one tab labelled with the topic title,
     slice null.
   Guard every label: trim it, and when the result is empty substitute a positional fallback
   such as `Part 3` so a blank authored title can never render an unlabelled tab.

3. `class SubtopicTabsView extends StatefulWidget` — taking `required ResourceTopic topic`,
   `Chapter? chapter`, and an optional `int initialIndex` defaulting to 0. Behaviour:
   - Compute the tab list once in `initState` and recompute it in `didUpdateWidget` when the
     incoming topic or chapter identity changes. The chapter arrives asynchronously, so the
     tab count changes from 1 to N mid-life: when the count changes, dispose the old
     `TabController` and build a new one with the new length, clamping the retained index into
     range. Never let the controller's length drift from the children count — that assertion
     failure is the main hazard in this widget.
   - When the derived list has one entry or fewer, render that single body alone with no tab
     strip, so a one-sub-topic topic does not get a lone stub tab.
   - Otherwise render a `Column` of a scrollable `TabBar` (labels from the derived list) above
     an `Expanded` `TabBarView` holding one body per entry. Leave `TabBarView`'s physics
     argument unset so it keeps Flutter's default horizontal drag behaviour — the sideways
     swipe between sub-topics is the entire feature of this task, so do not pass any physics
     that suppresses dragging, and do not wrap the view in a gesture detector that would win
     the horizontal drag arena.
   - Body for an entry that has a slice: a `ListView` padded at the bottom by
     `24 + bottomViewportInset(context)`, containing `topic.description` as body text when it
     is non-null **and this is the first tab only** (so the topic blurb is preserved exactly
     once instead of repeated on every tab), then `ReaderContent(chapter: slice, bookId: '')`.
   - Body for an entry with no slice: a padded, scrollable placeholder built from
     `widgets/common/coming_soon.dart` — a `ComingSoonBadge`, the sub-topic label as a heading,
     and one muted sentence (styled with `ComingSoonStyle.body`) explaining that this part of
     the topic has not been written yet while the rest of the station is still browsable. Use
     `kComingSoonLabel` for the phrase rather than typing it inline.
   - Give each body a `PageStorageKey` derived from the tab label so scroll position survives
     swiping away and back.

Then rewire `osce_screen.dart` end to end:
   - `OsceScreen`'s `ListView.builder` keeps its current tile rendering (including the
     coming-soon treatment from sibling 260918-dqy — do not restyle it), but its `onTap` now
     pushes the detail screen for the tapped `ResourceTopic` itself rather than an index into

   - `_OsceDetailScreen` takes `required ResourceTopic topic`. It loads only that topic's

     non-null), holding `Chapter?` and `Object?` error state for that one topic instead of the

   - Its `AppBar` title becomes the opened topic's title. Its `bottom` tab strip and the

     while the fetch is in flight, the existing centred "Could not load this section." message
     on error, and otherwise `SubtopicTabsView(topic: topic, chapter: loadedChapterOrNull)`.
   - Delete `_OsceTabBody` and `_OutlinePlaceholder`: the per-sub-topic placeholder inside
     `SubtopicTabsView` now covers the content-less station case, one tab per outline entry
     instead of one checklist of all of them. Leave a short comment on the detail screen
     recording that stations with no content JSON still open, because their outline is real
     structure and now forms the tabs.

Update `test/screens/osce_screen_test.dart` to the new contract per `<behavior>`. Resolve
