## Area 1 - Practice session flow

### Observed behavior

`ExamPrepHomeScreen._load()` loads the question bank, the user's exam-prep access flag, previously recorded answers, and a single next question from `NextQuestionSelector`, seeding the on-screen option order from `Object.hash(question.id, review?.attempts ?? 0)` (enchiridion/lib/screens/exam_prep_home_screen.dart). The home screen's "Quick Check" card offers exactly one entry point, a "Practice one now" button, which pushes `QuestionScreen` with `onAnswered` wired to `_handleStudyCardAnswer` (records the answer locally and re-picks the next question) and `onRequestNext` wired to `_serveNextQuestion` (hands over the already-picked next question without invoking the selector a second time) (enchiridion/lib/screens/exam_prep_home_screen.dart). Inside `QuestionScreen`, selecting an option and tapping Submit calls `_submit()`, which records the `UserAnswer` through `StorageService.recordAnswer`, then (when `trackDailyStudyStats` is set) through `StudyStatsProvider.recordAnswer`, then invokes `widget.onAnswered`, then fires two best-effort background calls, `NotificationService.scheduleFollowUp` and `QuestionReviewSyncService(storage).push` (enchiridion/lib/screens/question_screen.dart). Feedback renders immediately below the options: a green/red "Correct!"/"Incorrect" banner, an "Explanation" section rendered through `ExplanationText` (which preserves literal newlines per sibling 260917-ndr), and an optional teal "OSCE Tip" box when `question.osceTip` is set (enchiridion/lib/screens/question_screen.dart, enchiridion/lib/widgets/exam_prep/explanation_text.dart). When `onRequestNext` is supplied and the screen is not read-only, submitting starts a fixed six-second auto-advance countdown (`_feedbackPause`) showing "Next question in Ns", a "Next question" button, and a "Stay on this question" cancel control; on expiry `_advance()` awaits the loader and swaps `_question`/`_optionSeed` in place, or sets `_exhausted = true` and shows "You're all caught up — nothing more is queued right now." when the loader returns null (enchiridion/lib/screens/question_screen.dart). Leaving the flow otherwise is only "Back to question list" (`Navigator.pop`). The book-scoped `QuestionListScreen` (used for per-book question banks, not the standalone exam-prep scope) shows only previously-answered questions via `reviewableQuestions`, with a padlock icon on anything past `kFreeQuestionCount` (enchiridion/lib/screens/question_list_screen.dart, enchiridion/lib/services/question_visibility.dart). The former whole-bank browsing screen no longer exists in this tree at all — `git log --diff-filter=D --oneline -- '*exam_prep_question_list_screen.dart*'` shows it deleted in commit 66b6a80, sibling 260917-ndx's work. The Android bubble window renders the same one-question flow through a separately implemented `QuickCheckCard`, with its own Submit/Skip/Close controls and no auto-advance or next-question chaining at all (enchiridion/lib/widgets/exam_prep/quick_check_card.dart, enchiridion/lib/bubble_main.dart).

### Findings

A practice session has no defined start or end: opening Exam Prep serves exactly one question at a time from the home screen's Quick Check card, with no "how many questions in this session" framing, no progress indicator, and no session summary — the six-second auto-advance is the only through-line, and cancelling it just returns to the same single-question card with nothing to work toward. The "Next question in Ns" auto-advance timer runs on a fixed six seconds regardless of explanation length (enchiridion/lib/screens/question_screen.dart, `_feedbackPause`), forcing a user who wants to actually read the OSCE tip to consciously tap "Stay on this question" every single time, which is friction hidden inside a feature meant to remove friction. There is no self-rated confidence input anywhere in the answer flow — `_submit()` builds `UserAnswer` from only `isCorrect`, and `QuestionReview.applyAnswer`'s `confident` parameter (which exists specifically to distinguish a guess from real knowledge and route to `guessedInterval`) is never passed a non-default value from any of the three answer-recording call sites, so a lucky guess is scheduled on the ladder identically to a knowledge-based correct answer. The bubble `QuickCheckCard` duplicates almost all of `QuestionScreen`'s submit/explanation rendering with its own separate `State` class and stops at Close — even though the same `NextQuestionSelector` that powers the home screen's advance could hand the bubble window another question immediately, a user who has the bubble open and wants to keep going has no way to.

### Recommendations

#### R-01: Give the practice session an explicit shape
Turn "Practice one now" into a bounded practice set — e.g. offer a 10-question run with a visible "N of 10" progress indicator on `QuestionScreen`'s app bar and a session-end summary card (answered, correct, points earned this run) once the set completes, instead of an undifferentiated stream of single questions. This sits directly on top of 260917-ndv's existing in-place advance mechanism (`onRequestNext`/`_advance()` in enchiridion/lib/screens/question_screen.dart already swap the question without leaving the route) — it only needs a counter and a terminal state layered over that plumbing, not a new advance mechanism.

#### R-02: Gate the auto-advance pause on self-rated confidence
After submit, offer an inline "Sure / Guessed" choice instead of (or before) starting the fixed six-second countdown, and thread the answer into the `confident` parameter `QuestionReview.applyAnswer` already accepts but which the practice flow never supplies (enchiridion/lib/models/question_review.dart). This makes the existing `guessedInterval` branch actually reachable from real user behavior, and lets the pause length reflect how sure the user was rather than a flat six seconds for everyone.

#### R-03: Let a bubble Quick Check answer chain into another question
Extend `QuickCheckCard`/`bubble_main.dart` so a submitted bubble answer can load a second question via `NextQuestionSelector.next()` and swap it in place, instead of ending every bubble interaction at Close or Skip (enchiridion/lib/widgets/exam_prep/quick_check_card.dart, enchiridion/lib/bubble_main.dart). This keeps the bubble's "one light question, minimal chrome" character intact while giving a user who wants to keep going in that small window a way to, without forcing them back into the full app.

## Area 2 - Freemium question limit

### Observed behavior

`kFreeQuestionCount` (10) is a single constant in enchiridion/lib/config/freemium_config.dart. `AccessService.hasExamPrepAccess()` checks a Supabase-cached entitlement map, defaulting to false (free tier) whenever the user is signed out, offline, or Supabase is unconfigured (enchiridion/lib/services/access_service.dart). `NextQuestionSelector.next()` computes the eligible bank as `bank.where((q) => hasAccess || q.questionNumber <= kFreeQuestionCount)` before any due/lapse/unseen bucketing happens (enchiridion/lib/services/next_question_selector.dart) — for a free user, the entire spaced-repetition system (buckets, cooldown, least-recently-seen fallback) operates on exactly those 10 questions for as long as the account stays unpaid. On `ExamPrepHomeScreen`, the "Access" card shows either "Full access is active." or "You get 10 free practice questions. Unlock for unlimited practice." with an "Unlock" button that pushes `UnlockScreen` (enchiridion/lib/screens/exam_prep_home_screen.dart). Sibling 260917-ndx already removed the only surface that could browse the wider bank (`exam_prep_question_list_screen.dart`, confirmed deleted in commit 66b6a80), and sibling 260917-ndq already removed the bank-size disclosure elsewhere in the review flow, so a free user genuinely cannot see or measure the locked portion of the bank today — the only visible number is the fixed "10" in the Access card's own subtitle. `UnlockScreen` offers a book-specific plan, a monthly subscription, and a yearly subscription, each behind `PaymentService.purchase()` (enchiridion/lib/screens/unlock_screen.dart).

### Findings

When the selector serves nothing (`NextQuestionSelector.next()` returns null — e.g. a free user's ten questions are all inside the 90-minute cross-surface cooldown), the Quick Check card falls back to the generic line "No unlocked quick-check question is available yet." (enchiridion/lib/screens/exam_prep_home_screen.dart) with no Unlock affordance anywhere near it, even though the Access card two sections above already has one — a free user who hits this state has to scroll back up and connect the dots themselves. There is no distinction in the UI between "you are briefly cooling down" and "you have graduated (retired) every one of your ten free questions and there is nothing left to earn"; `NextQuestionSelector._leastRecentlySeen` quietly keeps re-serving retired questions from the free pool as a fallback (enchiridion/lib/services/next_question_selector.dart) rather than ever announcing that the free set has been mastered, so the freemium wall never actually announces itself; it just goes quiet. Because the free-tier filter lives inside the single shared selector rather than being surfaced anywhere in the UI, the freemium boundary is legible only by reading `next_question_selector.dart`, not by using the app.

### Recommendations

#### R-04: Point the empty Quick-Check state at Unlock for free users
When `_randomQuestion` is null and `_hasAccess` is false, replace the flat "No unlocked quick-check question is available yet." text with copy that names the free-tier ceiling and repeats the Unlock button already used on the Access card (enchiridion/lib/screens/exam_prep_home_screen.dart), so the moment a free user actually hits the wall is also the moment they are shown the door, not a shrug.

#### R-05: Show a mastery state when the free question pool is fully retired
Detect the specific case where every question in the free tier's `unlocked` set is `retired` (enchiridion/lib/services/next_question_selector.dart, enchiridion/lib/models/question_review.dart) and surface a one-time "You've mastered your 10 free questions" card in place of silently re-serving graduated content, turning an invisible plateau into a legible, positively-framed upsell moment.

## Area 3 - Study-mode notification delivery

### Observed behavior

Ambient prompting runs entirely outside the open app: `BubbleAlarmWorker` (native Kotlin, backed by WorkManager) re-enqueues itself every `MIN_DELAY_MINUTES` (18) plus a random `JITTER_MINUTES` (18) minutes — 18 to 35 minutes — first arming 3 minutes after app start via `armOnAppStart` (enchiridion/android/app/src/main/kotlin/com/example/enchiridion/BubbleAlarmWorker.kt), called from Dart through `BubbleScheduler.armOnStartup()` (enchiridion/lib/services/bubble_scheduler.dart). Each run boots a fresh headless Flutter engine and executes `bubbleAlarmCallback`, which checks for a signed-in user, probes exam-prep access with a bounded 10-second timeout, asks the same shared `NextQuestionSelector` for a question, and calls the native `showBubble` method channel with a teaser built by `notificationTeaser()` (enchiridion/lib/services/bubble_alarm_callback.dart, enchiridion/lib/services/notification_service.dart). Natively, `BubblePlugin.showBubble()` posts to a dedicated `quick_check` notification channel (`IMPORTANCE_HIGH`, required for Android to offer bubble expansion) with `BubbleMetadata` on API 30+, falling back to a plain notification otherwise (enchiridion/android/app/src/main/kotlin/com/example/enchiridion/BubblePlugin.kt). Tapping it opens `BubbleActivity`, whose engine runs `bubbleMain()` and shows `QuickCheckCard` directly (enchiridion/lib/bubble_main.dart, enchiridion/lib/widgets/exam_prep/quick_check_card.dart) — a separate flow from `NotificationService`, which only schedules the spaced-repetition follow-up reminder for a specific missed question on its own `exam_prep_review` channel, and whose `InAppStudyPromptHost` exists solely to catch a tapped fallback notification while the app is foregrounded (enchiridion/lib/services/notification_service.dart, enchiridion/lib/widgets/exam_prep/in_app_study_prompt_host.dart). No settings screen exists anywhere in `enchiridion/lib/screens/` and no code anywhere exposes the 18/35-minute cadence, the two channel ids, or notification-permission state to the user; the only user-facing lever is the operating system's own notification toggle.

### Findings

A user's only way to affect how often the ambient prompt fires, or to silence it, is the operating system's own per-app or per-channel notification settings, which the app never surfaces, links to, or mentions — someone who finds the cadence too frequent has to already know Android well enough to find "App info → Notifications → Quick Check" unaided. That is a real gap even though the plumbing half-solves it already: `BubblePlugin` posts ambient prompts on the separate `quick_check` channel while `NotificationService` posts spaced-repetition reminders on `exam_prep_review` (enchiridion/android/app/src/main/kotlin/com/example/enchiridion/BubblePlugin.kt, enchiridion/lib/services/notification_service.dart), so a user actually could silence just the ambient prompt without losing spaced-repetition rebounds — the app just never says that channel-level control exists. The 18-35 minute cadence and the first-run 3-minute delay are hardcoded native constants (enchiridion/android/app/src/main/kotlin/com/example/enchiridion/BubbleAlarmWorker.kt) with no in-app visibility, so a user who has had the app installed for hours with no prompt — the exact complaint sibling 260917-ndz's item was filed against — has no in-app way to tell whether that is expected jitter, a permission problem, or the delivery chain broken again; only external silence to go on.

### Recommendations

#### R-06: Add an in-app link to the ambient prompt's notification channel settings
Add a "Quick Check reminders" row (on the Exam Prep home screen or a new lightweight settings surface) that opens Android's channel-specific notification settings for the `quick_check` channel via an intent, since the channel separation `BubblePlugin` already implements (enchiridion/android/app/src/main/kotlin/com/example/enchiridion/BubblePlugin.kt) already supports silencing ambient prompts independently of spaced-repetition reminders — the capability exists, it is just undiscoverable.

#### R-07: Surface ambient-prompt delivery health in-app
Persist a "last ambient prompt posted at" timestamp from `bubbleAlarmCallback` (enchiridion/lib/services/bubble_alarm_callback.dart) into local storage, and show a small status line on the Exam Prep home screen ("Last study prompt: 22 min ago") so a user who has gone hours without one has an immediate, in-app diagnostic instead of only silence — a direct answer to the kind of report sibling 260917-ndz's delivery-path fix responded to, making the next occurrence of that failure mode visible from inside the app rather than only inferable from its absence.

## Area 4 - Stats and points feedback loop

### Observed behavior

Every answer that reaches `QuestionScreen._submit()` or `QuickCheckCard._submit()` records through `StudyStatsProvider.recordAnswer()`, which delegates to `StudyStatsService.recordAnswer()` and calls `notifyListeners()` synchronously before any network sync resolves (enchiridion/lib/providers/study_stats_provider.dart, enchiridion/lib/services/study_stats_service.dart). `StudyStatsService.recordAnswer()` only updates `questionsAnswered`/`correctAnswers`/`performancePoints` when `isFirstAttempt` is true (`review.attempts == 1`), awarding a flat 10 points for any first correct answer and 0 otherwise, then best-effort syncs the day's row to Supabase's `daily_study_stats` table (enchiridion/lib/services/study_stats_service.dart). `ExamPrepHomeScreen` watches `StudyStatsProvider` and renders four tappable pills — Answered, Correct, Wrong, Points — each of which (per sibling 260917-nds) opens `AnsweredQuestionsScreen` filtered accordingly, plus a "Today: N answered, N points" line (enchiridion/lib/screens/exam_prep_home_screen.dart). `AnsweredQuestionsScreen` computes its own all-time answered/correct/wrong counts directly from the stored answer map and duplicates the points-per-answer constant in its own `kCorrectAnswerPoints`, with a comment explaining the duplication is deliberate because this plan may not edit `study_stats_service.dart` (enchiridion/lib/screens/answered_questions_screen.dart). `StudyStatsTotals.fold()` sums every stored day's stats into the lifetime headline figures the dashboard shows (enchiridion/lib/models/study_day_stats.dart). Separately, `LeaderboardService.fetch()` calls a `get_leaderboard` Supabase RPC to rank users (enchiridion/lib/services/leaderboard_service.dart). Each `Question` already carries an optional `topic` string (enchiridion/lib/models/question.dart), but nothing in `StudyDayStats`, `StudyStatsTotals`, or `AnsweredQuestionsScreen` groups by it.

### Findings

The points figure rewards volume, not skill or difficulty — a flat 10 points for any first-attempt correct answer means a lucky guess is worth exactly as much as a confidently-earned correct answer at the top of the spaced-repetition ladder (enchiridion/lib/services/study_stats_service.dart, enchiridion/lib/models/question_review.dart's `stageIntervals`), so the dashboard number cannot be read as "how much do I actually know," only "how many questions have I clicked through." There is no concept of a streak anywhere in the stats code (`StudyDayStats`/`StudyStatsService`/`ExamPrepHomeScreen` never reference consecutive-day study), even though the per-day `StudyDayStats` records already exist and are keyed by calendar date — exactly the data a streak needs, unread that way today. `Question.topic` is populated in the data model but entirely unused for feedback — a user weak in one specialty and strong in another gets no indication of that from any stats surface, only an undifferentiated Answered/Correct/Wrong/Points total. The leaderboard is the one place score comparison against other users happens, but nothing on `ExamPrepHomeScreen` links to it except a small icon-only app-bar button (enchiridion/lib/screens/exam_prep_home_screen.dart), so it is easy to never notice it exists.

### Recommendations

#### R-08: Add a study streak with a one-day repair allowance
Compute a consecutive-day streak from the existing per-day `StudyDayStats` records (`StorageService.getAllDailyStudyStats`, enchiridion/lib/models/study_day_stats.dart) and show it alongside the existing metric pills, with a one-day grace/repair window so a single missed day does not zero out weeks of consistency — the underlying data already exists; this only adds a derived read and a small UI element, no new storage schema.

#### R-09: Add a per-topic accuracy breakdown
`Question.topic` (enchiridion/lib/models/question.dart) is already populated per question but never aggregated; group the existing per-question answer/review records by topic inside `AnsweredQuestionsScreen` (enchiridion/lib/screens/answered_questions_screen.dart) to show e.g. "Genetics: 8/10, Cardiology: 3/9" from data the app already stores, closing the "what am I actually weak in" gap the flat Answered/Correct/Wrong tiles leave open.

## Area 5 - Retry and review flow

### Observed behavior

`QuestionReview` is the single source of truth for what gets served next, separate from the raw `UserAnswer` history (enchiridion/lib/models/question_review.dart). A wrong answer resets `stage` to 0, increments `lapses`, and schedules `dueAt` a jittered `relearnInterval` (1 day) later via `applyAnswer()` (enchiridion/lib/models/question_review.dart) — the 24-hour requeue sibling 260917-ndy shipped. A correct-but-unconfident answer holds position and reschedules 8 hours out (`guessedInterval`); a correct-and-confident answer advances one stage on `stageIntervals` (1, 3, 7, 21 days) and retires the question once it clears the top stage. `NextQuestionSelector.next()` partitions the unlocked bank into `lapsedDue` (a real past miss, sorted by due date), `freshDue`/`unseen` (alternated by the shared `ServeLog.counter`'s parity so neither backlog nor new material starves the other), and falls back to `_leastRecentlySeen` — which still respects an open lapse window (`review.lastCorrect == false && review.dueAt.isAfter(now)` is skipped) — when nothing else is servable (enchiridion/lib/services/next_question_selector.dart). `ServeLog` tracks only the twelve most recently served ids for cross-surface cooldown spacing, with no other history (enchiridion/lib/models/serve_log.dart). None of `lapsedDue.length`, `freshDue.length`, `unseen.length`, or any due-count is read by any screen — `ExamPrepHomeScreen` only ever asks the selector for one question at a time and never inspects the backlog it came from (enchiridion/lib/screens/exam_prep_home_screen.dart). The only place a missed question becomes revisitable on the user's own initiative, rather than waiting for the scheduler, is `AnsweredQuestionsScreen`'s Wrong filter, added by sibling 260917-nds, which opens the question read-write (`readOnly: answer.isCorrect` is false for a wrong row) so retrying it re-runs `applyAnswer()` (enchiridion/lib/screens/answered_questions_screen.dart).

### Findings

The spaced-repetition schedule that actually governs what a user sees next is completely invisible from any screen — there is no "3 due for review, 5 new" style count anywhere, so a user cannot gauge whether they are caught up, behind, or about to be shown something old versus new; the only view into the schedule is reading the source in `next_question_selector.dart`. A missed question does feel recoverable in the sense that it is guaranteed to come back (the 24-hour requeue, plus the on-demand Wrong-filter retry), but nothing tells the user that guarantee exists — closing the app right after a miss gives no confirmation it is now scheduled for tomorrow rather than lost, which reads as broken from the outside even though the backend is correct. `NotificationService.scheduleFollowUp` books one local notification per lapsed question, keyed by `Object.hash(scope, questionId)` (enchiridion/lib/services/notification_service.dart) — a day with several misses produces that many separate notifications stacking on top of the independently-running ambient bubble alarm, all arriving in the exact window when the user is, by definition, already behind on the material.

### Recommendations

#### R-10: Show a visible due-and-backlog count on the Exam Prep home screen
Surface the counts `NextQuestionSelector` already computes internally — due-for-review and new/unseen — as a simple line on the home screen, building on the metric-tile pattern sibling 260917-nds introduced for Answered/Correct/Wrong/Points, so the spaced-repetition schedule that silently governs what gets served next is finally visible to the person it is scheduling for (enchiridion/lib/services/next_question_selector.dart).

#### R-11: Batch a lapse-heavy day's rebounds into one "Catch-up" bubble
When several `QuestionReview`s become due for relearn within the same rough window, detect that in `bubbleAlarmCallback`/`NotificationService.scheduleFollowUp` and post a single "Catch-up: N questions to review" bubble/notification that opens `AnsweredQuestionsScreen`'s Wrong filter directly, instead of stacking one notification per lapsed question (enchiridion/lib/services/notification_service.dart) on top of the independently-running ambient alarm — a genuinely offline/bubble-specific answer to "does a missed question feel recoverable" that most competing spaced-repetition apps solve only with a single badge count rather than a batched delivery.
